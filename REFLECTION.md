Group Reflection (solo group, UG)

Problem and requirements. SmartCare is a session booking system. My tasks were to find patients and practitioners by ID, cancel appointments without losing the appointment history (FR-06, FR-07), and make sure that a practitioner is not double booked (FR-05). I assigned each piece to an issue and acceptance criteria, including AC-04.1 and AC-04.2, to ensure that each test could be linked to a requirement. Understanding that absence means LookupError while invalid input means ValueError was the key contract.

Design and implementation. The design separates responsibilities. The cancellation rule is owned by the Appointment domain object, the data store only stores objects and returns None if the ID is not found, and the services coordinate them. I kept the service methods short: find_patient, find_practitioner and cancel_appointment each look up the object, raise LookupError if it is not found, and call the domain method instead of setting a status themselves. I didn't want to combine the two almost identical lookup methods into a single helper, since three lines of code were not enough to warrant the additional abstraction.

Testing, debugging and improvement. In Stage 6 I wrote 22 service tests and in Stage 7 I wrote 46 more, plus 8 tests that were supplied, for a total of 76 passing tests on main. I checked that tests can fail for the right reason, for example, if a second cancellation stops raising ValueError, T-623 fails. A Claude review found unused setup lines in T-627, which I removed, and the suite was rerun after each merge. I did not complete Stage 8: the preparation utility that plants the two defects was not available to me and I was unable to contact the tutor before the deadline, so I did not claim any debugging results. The tutorial and formative parts of that record are complete.

AI engineering judgement. I made my own observations and then used GitHub Copilot Free for the two required comparisons. I used its output as hypotheses and tested them. Its Stage 6 concern about unverified test coverage was partly correct, as I hadn't shown it the tests. Its Stage 7 candidate for another practitioner at the same time looked convincing, but its assertions compared an ID with itself and could hardly fail, and my retained test compares the stored objects and the full list. Copilot also stated that it was not possible to create a COMPLETED appointment using the public contracts; my T-764 does it. I never took confidence in an answer as evidence.

Professional and responsible practice. I used a public repository and only synthetic data, linked each change to an issue and pull request, and wrote a self-review before merging, as this is an approved solo group, which I noted as a limitation. I did not hide gaps; I described them, and I did not describe any Copilot use that did not happen. One thing that is still a concern is that my student-ID email is in the public Git history.

Learning and future practice. I learned to read the requirement before the code, to reproduce a problem before changing anything, and to check an AI answer against the real files instead of trusting it. The next time I would get the Stage 8 materials earlier, ask for the review arrangement at the beginning, use fixtures to reduce repeated test setup, and write my own hypotheses first and then use the AI to help me test them.
